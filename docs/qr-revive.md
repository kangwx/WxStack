# 手机扫码复活

失败结算包含「扫码复活」「重新开始」「返回首页」。每局可复活一次，不额外消耗体力；手机只打开扫码网页不会触发复活，点击「确认复活」后游戏才恢复。保留下方已叠好的塔、分数、昵称和本局完美次数，移除失败的方块，将塔顶承接块和新方块的宽、深都恢复为初始最大尺寸的 50%（各 2.5），厚度不变，再从当前层继续。重新出现的方块有入场保护。复活后再次失败不会重复发放金币，也不会产生两条同局排行榜记录。

## 本地启动

```sh
npm ci
npm run revive:serve
```

服务默认监听 `0.0.0.0:7461`，打印可供手机访问的局域网地址。手机和电脑需要连到同一网络；有客户端隔离的 Wi-Fi 不能互访。服务同时提供 `build/web-mobile` 构建页面，可在打印的地址直接打开游戏。Creator 的 `localhost:7456` 预览默认连接同一电脑的 `7461` 服务。

有多个网卡或需要固定访问域名时设置：

```sh
REVIVE_PUBLIC_URL=http://192.168.1.8:7461 npm run revive:serve
```

将示例 IP 换成手机实际可访问的地址。`REVIVE_PUBLIC_URL` 是写入二维码的地址，`PORT` 和 `HOST` 控制监听端口与地址。部署到线上时，需要运行该 Node 服务并通过 HTTPS 反向代理；在游戏启动脚本之前设置 `window.WXSTACK_REVIVE_SERVICE = 'https://你的复活服务域名'`，同时将服务端 `REVIVE_PUBLIC_URL` 设置为同一个可公开访问的 HTTPS 地址。仅发布静态游戏文件不能完成跨设备确认。

## 协议与状态

- 创建二维码：`POST /api/revive`。返回随机会话 ID、游戏端凭证、过期时间、扫码链接及二维码模块。二维码只含手机确认凭证，不包含游戏端消费凭证。
- 手机确认：`POST /api/revive/:id/confirm`，使用扫码链接片段中的确认凭证作为 Bearer token。
- 游戏检查：`GET /api/revive/:id`，使用游戏端凭证。确认后调用 `POST /api/revive/:id/consume`，只能成功消费一次。
- 取消：`DELETE /api/revive/:id`。关闭二维码、离开当前局或销毁组件后，旧响应不能触发复活。
- 会话保存在服务端内存，5 分钟过期；服务重启后需要重新生成二维码。掉线可重试，也可以返回结算。客户端每秒查询一次，单次请求最多等待 8 秒。

服务只接收随机复活凭证，不上传昵称、分数、金币或体力存档。它提供跨设备确认，不验证广告观看或支付，也不是联网游戏的防作弊系统。

## 验证

运行 `node --test tools/test-*.cjs`。测试覆盖确认与消费凭证隔离、重复确认、重复消费、过期、取消、旧回调、当前塔恢复、体力不扣除、金币增量、同局榜单更新和三按钮响应式布局。

手动流程：开始游戏并落空 → 打开扫码复活 → 手机扫描 → 确认复活 → 游戏恢复 → 再次失败时不能再次复活。还需验证关闭二维码后再在手机确认不会恢复游戏，以及服务未启动时可正常返回结算。
